佣金数据看板 · 需求与业务逻辑说明

核心目标：把「订单产生的应付佣金」与「人力 / 财务实际付出的实付佣金」放在同一个可自助查询的面板里，按人员、队伍、岗位、商品、月份多维交叉对比，让业务方一眼看出该发多少、实发多少、差在哪、为什么差。
应付≠实付订单一产生就有应付，实付受发放资格、签约、时间差影响，两者必须分开统计再核对。
支付通道：过渡期认领制人力系统与后台打通前，应付先交人力人工认领订单，认领部分＝人力付；其余＝财务付。实付数据与应付基本一致，只多「付没付」标记。
维度并列可交叉员工/非员工、孵化/素人、队伍、岗位、商品是并列维度，不是互斥分类。
佣金有延后性订单完成后 +10 个自然日才满足结算：图书看确认收货（主动 / 物流签收后 7 自然日系统确认），999 原生营付款成功即完成。
不发放有据可依官方号/白名单、班主任 999、公职不签约等会造成应付有、实付无。
要自助查询不做每日推送，做成可筛选、可下钻、可导出的网页面板。

1需求全景：看板要回答的六个问题

按业务方原话归纳：先知道「该发多少」，再知道「实发了多少」，最后知道「差在哪、为什么」。

树状图：看板内容分成应付、实付、核对三大块，每块再拆到可查询的最小粒度。
  • 佣金数据看板 自助查询 · 月度环比 · 可导出
    • ① 应付 订单维度，客观产生
      • 人员身份
        • 员工 有企微
          • 按队伍：1—5 队
          • 按岗位：班主任 / 启蒙老师 / …
        • 非员工创作者 无企微
          • 按队伍：含达人队
          • 签约 / 未签约
      • 孵化属性
        • IP 孵化 已纳入培训
        • 纯素人 未接触
      • 商品
        • 999 训练营
        • 图书
          • 按书名拆分
      • 时间
        • 订单月 / 结算月 / 支付月
    • ② 实付 钱真正发出去
      • 人力支付 认领订单
        • 实付人数 / 金额
        • 应发未发人员
        • 拆商品
      • 财务支付 其余订单
        • 发放明细：每人多少
        • 第三方平台费用预估
        • 拆商品
    • ③ 核对与差异 核心
      • 应付 vs 实付
        • 一对一匹配
        • 有应付无实付
        • 金额不一致
      • 差异原因线索
        • 官方号 / 白名单
        • 岗位本身不发
        • 未签约 / 拒收
        • 跨月时间差
    • ④ 分析延伸 后续，非本期必做
      • 月度环比：谁涨了、谁跌了
      • 退款率异常：售卖节奏问题
      • 佣金预算预估
      • 素人挖掘：给 IP 组反向线索
      • 提醒签约：未签约名单推给助教
「员工 / 非员工」与「孵化 / 素人」是两个并列维度，各自都能覆盖全部人员；队伍维度同时存在于员工与非员工身上。

4三张数据表的关系

一张应付总表 + 两张实付表。三者靠「人」关联，靠「金额」核对；能否关联到订单取决于实付表字段。

关系图：应付总表是源头，人力表与财务表是结果，看板做对照。

① 应付总表 源头

订单级分佣流水，含正负向
项内容
谁触发用户下单（系统自动生成）
依赖分佣规则、商品、人员身份
产出每笔订单的应付佣金
影响谁业务方汇总 → 人力 / 财务付款

② 人力支付表 认领订单

过渡期由人力从应付中人工认领订单后发放（人力系统与后台打通中）
项内容
谁触发人力部门按月付款
依赖应付汇总 + 发放资格判定
产出员工实付金额、应发未发名单
影响谁员工本人、业务方核对

③ 财务支付表 其余订单

无企微的人，由财务经三方平台发放
项内容
谁触发财务部门按月付款
依赖应付汇总 + 创作者已签约
产出每人发放明细 + 平台费用
影响谁创作者本人、成本核算
已知可用字段（9 月样本实测）：人员＝用户ID / 手机号（610/610 全覆盖）、实名；订单＝来源单据ID；商品＝商品ID。未知：人力表与财务表是否含这些字段 —— 决定能否下钻到订单级。

5统计维度：并列、可交叉

业务方明确：这些维度不是互斥分类，任何人同时拥有多个标签，看板要能任意组合筛选。

树状图：人员身上同时挂着「支付方式 / 队伍 / 岗位 / 孵化属性」四类标签；商品与时间独立。
  • 一个分佣对象 同时具备以下全部标签
    • 标签一：支付身份
      • 员工 多为人力付（过渡期认领制）
        • 岗位子分类
          • 班主任 999 属职责内，不额外发
          • 启蒙老师
          • 助教 / 督导 / 其他 名单待补
      • 非员工创作者 无企微 → 财务付
        • 已签约 可发放
        • 未签约 暂缓，需催签
        • 公职人员 无法签约，不发放
    • 标签二：队伍归属 员工与非员工都可能有
      • 1—5 队 名称待补
      • 第六队 · 达人队 博轩负责
      • 无队伍
    • 标签三：孵化属性
      • IP 孵化 已纳入培训体系
        • 含员工 + 非员工
      • 纯素人 未接触、野生
    • 标签四：商品
      • 999 训练营
      • 图书 按书名拆
        • 4 本 口径待确认
两条等式（业务方原话）：员工 + 非员工 ＝ 全部人员；IP 孵化 + 纯素人 ＝ 全部人员。因此这两个维度是十字交叉，不能做成单一分类下拉。

8不发放的判定分支

这些是造成「应付有、实付无」的具体情形，来自业务方口述，判定条件尚需逐条书面确认。

分支图：每一类情形对应一种差异表现，看板只提示线索，不自动定性为异常。
  • 应付有 · 实付无
    • 账号性质
      • 官方号 / 白名单 产生佣金但不发放
      • 公益直播等场景 不发放
    • 岗位原因
      • 班主任卖 999 职责内，不额外发
    • 身份限制
      • 公职人员 不能签兼职合同，主动放弃
      • 创作者未签约 需催签后补发
    • 时间原因
      • 未到支付周期 完成后 +10 自然日
      • 跨月发放 订单月 ≠ 支付月
    • 数据问题
      • 人员归类错误 业务方提供纠正名单
      • 映射缺失 无法关联人员 / 商品
另有两类差异形态：
金额不一致 人对上了但金额不同 —— 退款冲减、平台费用、比例调整、多笔合并支付。
有实付无应付 发了钱但应付表找不到 —— 跨期补发、归类错误。

8.5特殊场景：发放角色切换（分段结算）

人的员工 / 创作者身份可能在月中切换，佣金按行为发生时的身份分段结算。口径来源：韩浩旭 2026-09-09 群内说明，2026-10-22 并入。

场景 A · 员工 → 离职 → 次月参与分佣
在职期间：按工资结算发放。
离职之后：按创作者规则结算发放。
同一个人同一个月出现两种结算方式。
场景 B · 创作者 → 入职 → 次月参与分佣
暂无此类案例。
先在流水上记录发放角色，待实际发放时再确认具体方式。
不为未发生的场景写死规则。
面板实现要求
流水上保留 「发放角色」字段；切换月的人员分段展示（在职段 / 离职段），支持按段筛选与导出。

9待确认问题

原文存在歧义、冲突或信息缺失的条目，需业务方逐条书面确认后进入开发。

A · 人员与组织

  1. 6 个队的正式名称与编号：已知 1—5 队 + 达人队（博轩），中间是否有其他名称；后台字段实测出现 11 个部门值，如何映射。
  2. 非员工是否也归队：口述「非员工也可能属于某队」，但队伍名单由谁维护、是否覆盖纯素人。
  3. 岗位完整分类：班主任、启蒙老师之外还有哪些；岗位与部门字段是否同一个来源。
  4. IP 孵化名单来源：由一心 / 冠鹏 / 博轩提供？IP 工作台后续是否自动同步？当前网站上看不到该名单。
  5. 孵化名单是否含员工：口述「IP 孵化里混杂员工与创作者」，名单需标注身份。
  6. 公职人员识别方式：靠什么字段或名单判断「不签约、不发放」。
  7. 小组助教关联规则：默认创作者都是 7 万课会员因而有助教，但存在活动放开的例外，例外如何处理。

B · 规则与口径

  1. 班主任 999 不额外发放：判定字段是什么？是否覆盖全部 999 订单？是否同样适用于其他岗位。
  2. 白名单 / 官方号清单：后台白名单功能不完善，当前清单从哪来、由谁维护、如何更新。
  3. 不发放场景是否还有其它：口述提到「公益直播等」，完整清单待补。
  4. 图书 4 本 vs 5 个商品名：口述前后提到 3—4 本书、5 个商品名，以哪个为准。
  5. +10 个工作日规则 → 已更正（10-22）：订单完成后 +10 个自然日，统一适用。
  6. 三种月份口径：环比与趋势用订单月、结算月还是支付月；退款金额归属哪个月。
  7. 6.8% 平台费用：是税费还是手续费？计算基数是什么？是否仅财务侧？是否计入本看板成本。

C · 数据与系统

  1. 人力表与财务表的字段清单：是否含人员 ID、手机号、订单号；决定能否关联到订单级。
  2. 实付能否关联具体订单：应付表结算时间、结算单号全为空，实付侧是否提供批次或单号。
  3. 签约状态字段来源：哪个系统可取，多久更新一次。
  4. 「归类有问题的老师」纠正数据：格式、提供频率、如何回写。
  5. 数据更新频率：月度还是实时；面板刷新机制。
  6. 导出范围与权限：含身份证号等敏感字段是否脱敏。
  7. 历史数据范围：目前确认有 7、8、9 月；另有 4、5 月数据是否纳入首期。

D · 需求边界

  1. 本期范围：预算预估、手续费预估入口是否放进第一版。
  2. AI 分析期望：口述希望 AI 自动发现退款率异常、售卖节奏问题，是否本期实现。
  3. 素人挖掘是否本期 → 已定：后续延伸，并追加「提醒签约」。
  4. 呈现形式：明确为自助查询网页，不做每日推送；是否支持导出与筛选组合。
  5. 是否需要同比：口述只要环比，未来是否加同比。
  6. 优先级归属：作为个人工作需求按正常排期，是否需要于老师确认。
